# 5.5 — Link actual money transactions to projects

**Status:** Planned  
**Goal:** Show project costs from actual ledger entries without creating a second source of financial truth.

## Link policy

- Use an explicit nullable `project_id` foreign key on a money transaction; do not add a generic polymorphic link table for this known relationship.
- A transaction links to at most one project in v1. Project actual cost is a view of linked ledger expenses, not a separate cost record or project-maintained total.
- A transaction remains part of normal team financial totals whether or not it is linked to a project. Project views filter those same transaction IDs; they do not add project costs again to team totals.
- Reversal/adjustment entries preserve the original project's link/classification so correction-aware net project cost matches correction-aware ledger totals.

## Acceptance checks

- [ ] Project actual costs are calculated from ledger records; there is no duplicated actual-cost field.
- [ ] A linked expense appears once in team ledger actuals and once as a related row in the project view, without the project subtotal being added a second time.
- [ ] Reversals and replacements produce the same net result in project and team-level financial totals.
- [ ] Existing transaction rows migrate with no project link and no fabricated costs.
- [ ] Optional project links are stable across project renames and archived-project state.

## Dependencies / boundaries

- Depends on Phase 4 ledger schema/repository/correction behavior, [5.1](5.1-project-schema-repository.md), ARCH-05, and ARCH-06.
- The link is optional and does not require a project for an expense.
- Event/part links and many-to-many cost allocation are not included; future link types need their own explicit integrity decision.
