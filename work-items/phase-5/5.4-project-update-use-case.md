# 5.4 — Add the project update use case

**Status:** Done  
**Goal:** Append a dated work update and, when supplied, change the project's current status atomically.

## Work list

- [x] Add a service operation that validates active-team project scope, project state, entered date, required summary, optional status label, and notes.
- [x] Reject updates to archived projects unless an explicit unarchive workflow is later designed.
- [x] When a status-change label is supplied, append the update and change the project's current status in one transaction; when absent, leave current status unchanged.
- [x] Append audit activity for the update and any current-status transition in the same transaction, using the registered project/update record kinds.
- [x] Preserve user-entered date independently from system creation time and avoid inferring a project completion date from a status label.
- [x] Add unit/service integration tests for validation, status/no-status updates, rollback at each write stage, history payloads, team scope, and archived-project behavior.

## Acceptance checks

- [x] Update, current-status change, and audit history commit together or not at all.
- [x] An update without a status change does not mutate the project summary or status.
- [x] A supplied status value remains a user-entered label; no progress percentage or inferred completion is produced.
- [x] Failed validation or persistence leaves both the project and timeline unchanged.
- [x] The operation is available without Notcurses and can be called by a future command route through the same use case.

## Dependencies / boundaries

- Depends on [5.2](5.2-project-use-cases.md), [5.3](5.3-development-update-schema-repository.md), ARCH-01, ARCH-05, and Phase 3 activity infrastructure.
- This is the application operation only; entry forms and detail presentation are in 5.7–5.8.
- No automatic project completion, cost entry, or progress calculation is included.
