# 5.2 — Add project create, edit, and archive use cases

**Status:** Done  
**Goal:** Apply project rules and preserve team-scoped history through shared application operations.

## Work list

- [x] Add create, edit, and archive service operations for project records.
- [x] Validate nonblank title, optional text normalization/length, date syntax, and any chosen target/actual-date consistency rule without silent truncation.
- [x] Validate that optional season/car references exist in the same team; keep existing references valid when the referenced records later become archived.
- [x] Treat category and status as normalized user-entered labels; do not require membership in a seeded or hard-coded workflow vocabulary.
- [x] Record create, changed-field edit, and archive activity with stable project record identity and only the relevant before/after fields.
- [x] Use shared transaction helpers so project mutation and activity history commit atomically.
- [x] Add pure validation and SQLite service tests for create/edit/archive, no-op edit, invalid/cross-team references, activity payloads, and rollback.

## Acceptance checks

- [x] Invalid or cross-team references produce structured validation errors and no database or audit writes.
- [x] Edits include only fields that changed; a no-op edit does not claim a change.
- [x] Archive preserves the project and its update/transaction links; default lists may omit it while detail/history can still reach it.
- [x] Audit event and project mutation either both commit or neither commits.
- [x] The service is testable without Notcurses and is the only write path used by UI/commands.

## Dependencies / boundaries

- Depends on [5.1](5.1-project-schema-repository.md), ARCH-01 transaction helpers, ARCH-05 project record-kind registration, Phase 3 reference services, and activity repository support.
- No project-specific UI or command route is added here.
- Archive is not hard deletion; no update may fabricate progress or an actual completion date.
