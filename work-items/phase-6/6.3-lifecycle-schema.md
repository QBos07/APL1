# 6.3 — Add fitment and lifecycle-event schema

**Status:** Planned  
**Goal:** Preserve dated component changes as durable events and derive current fitment from their history.

## Data policy

- Lifecycle actions are user-entered `install`, `remove`, `replace`, `repair`, and `dispose` events. Each has a stable ID, team scope, entered date, action, optional car/position/event label/reason/usage/notes, and system creation metadata.
- An install/remove/repair/dispose event references the affected unit. A replace event references both the old and new unit in one operation record; it appears in both unit histories.
- Current fitment is derived from valid lifecycle events; do not maintain a second editable fitment/balance-like field.
- Event association is optional and user-entered; until the event feature exists, retain the supplied event label rather than inventing or requiring an event record.

## Acceptance checks

- [ ] Schema creates no fitment/lifecycle rows or presumed current state.
- [ ] Every event preserves its entered date separately from system timestamps.
- [ ] A replacement is represented once with stable old/new unit IDs so it can be shown in both histories and carry one cost link.
- [ ] Lifecycle rows are append-oriented; schema does not provide a mutable “current part” field that overwrites prior history.
- [ ] Constraints reject malformed event shapes and cross-team links.
