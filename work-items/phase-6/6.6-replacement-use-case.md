# 6.6 — Add atomic replacement use case

**Status:** Implemented  
**Goal:** Replace a fitted unit while preserving one traceable transition and leaving the old fitment unchanged on failure.

## Work list

- [x] Add a replacement operation accepting team, car/position, old unit, new unit, entered date, and optional event/reason/usage/notes.
- [x] Validate the old unit is the currently recorded fitment at the selected car/position and the new unit is eligible and not fitted elsewhere/disposed.
- [x] Append one replacement lifecycle event referencing both old and new units and append its activity event in the same transaction.
- [x] Derive the new current fitment from that event; do not separately update a mutable fitment field.
- [x] Ensure any failure during validation, event append, audit append, or commit leaves prior fitment/history unchanged.
- [x] Add tests for valid replacement, wrong old unit, occupied/invalid new unit, same-unit replacement, ambiguity, rollback, both unit histories, and active-team isolation.

## Acceptance checks

- [x] A successful replacement changes the derived current unit exactly once and remains visible in both old/new unit histories.
- [x] A failed replacement leaves old fitment and all history unchanged.
- [x] Old-unit removal and new-unit installation are represented as one user-visible replacement operation, not two independently committable writes.
- [x] The operation records only user-entered date/reason/usage and does not infer performance or stock state.
