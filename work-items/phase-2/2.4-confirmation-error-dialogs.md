# 2.4 — Add reusable confirmation and error dialogs

**Status:** Not started  
**Goal:** Provide consistent, testable modal behavior for confirming risky actions and explaining failures.

## Work list

- [ ] Define dialog state and result values (confirmed, cancelled, dismissed) independently of drawing.
- [ ] Render a confirmation dialog with a clear action description and explicit confirm/cancel choices.
- [ ] Render an error/information dialog that can display a useful message without truncating it silently at the UI boundary.
- [ ] Support keyboard focus and mouse activation according to the Phase 2 focus/mouse decision.
- [ ] Make Escape/cancel dismiss without performing the pending action.
- [ ] Handle small terminal sizes with a bounded/reflowed dialog or clear fallback.
- [ ] Add tests proving confirm and cancel produce distinct results and that dismissal never invokes an action.

## Acceptance checks

- [ ] The caller receives an explicit dialog result and remains responsible for executing the confirmed operation.
- [ ] Cancel/dismiss cannot accidentally perform a destructive action.
- [ ] Keyboard and mouse users can reach the same choices, with visible focus.
- [ ] Error text is readable at supported sizes and does not silently disappear.
- [ ] Dialog state/result tests do not require Notcurses or SQLite.

## Dependencies / boundaries

- Depends on [2.0.1](2.0.1-tui-layout-resize-decision.md), [2.0.2](2.0.2-mouse-focus-decision.md), and [2.2](2.2-shared-screen-frame.md).
- This component does not decide business validation or execute database operations.
