# 2.27 — Implement navigation and team command actions

**Status:** Complete (2026-11-24)  
**Goal:** Make the command line useful in Phase 2 by supporting view shortcuts and complete/incomplete team actions.

## Work list

- [x] Register view/navigation commands such as `:view teams`, `:view overview`, and `:overview all`.
- [x] Register `:team list`, `:team switch <name-or-id>`, and `:team create` commands.
- [x] For unambiguous complete navigation/switch commands, execute immediately and update the same navigation/active-team state as mouse/keyboard menus.
- [x] For `:team create` with no name, open the create-team dialog; with a complete valid name, create directly through the same use case and activate the new team.
- [x] If command arguments are incomplete but meaningful, open the relevant dialog and prefill supplied values.
- [x] If a name is ambiguous, open a selection dialog; never choose an arbitrary team.
- [x] Register Help, About, and version-information navigation/actions so command users can reach top-bar content.
- [x] Test each handler via the same application/use-case operation used by the menu/dialog path.

## Acceptance checks

- [x] `:view ...` is a navigation shortcut and does not mutate domain data.
- [x] Complete `:team switch` changes active team once and returns to the same body tab.
- [x] Partial `:team create` opens a prefilled dialog; complete `:team create --name ...` validates and creates through the shared use case.
- [x] Ambiguous/invalid targets leave state unchanged and provide a clear choice/error.
- [x] Command and menu actions produce equivalent database state and audit behavior.
- [x] No handler contains SQL or duplicates team validation rules.

## Dependencies / boundaries

- Depends on [2.24](2.24-team-flows-as-dialogs.md), [2.26](2.26-command-parser-registry.md), and completed team use cases.
- Money, development, parts, and event commands are added with their corresponding feature phases/Phase 8.


## Verification (2026-11-24)

- `src/tui/action.{h,c}` maps parsed requests to typed navigation/team/help
  intents with no persistence. The shell dispatches them through the same
  `set_section`, `open_team_picker`, `perform_create`, and
  `apl_team_service_set_active` paths used by menus/dialogs.
- `:view`/`:overview` only navigate; complete `:team switch` resolves unique
  exact/prefix names or ids, refuses archived targets, and opens the picker for
  ambiguous prefixes; `:team create` opens the form without a name or creates
  directly with one; Help/About/Version open the same information dialogs.
- Failed/unknown/invalid commands leave view/team/data unchanged and show an
  explicit error; no handler contains SQL or duplicates domain validation.
- `tests/tui/test_tui_action.c` covers every Phase 2 intent. The smoke harness
  exercises cancel, navigation, incomplete form, direct create, switch,
  failure, duplicate validation, help/version, and mouse command invocation.
- `ctest --test-dir cmake-build-debug --output-on-failure`: 2/2 tests pass;
  `python3 scripts/smoke_tui.py --app cmake-build-debug/apl1`: passes.
