# 2.27 — Implement navigation and team command actions

**Status:** Not started  
**Goal:** Make the command line useful in Phase 2 by supporting view shortcuts and complete/incomplete team actions.

## Work list

- [ ] Register view/navigation commands such as `:view teams`, `:view overview`, and `:overview all`.
- [ ] Register `:team list`, `:team switch <name-or-id>`, and `:team create` commands.
- [ ] For unambiguous complete navigation/switch commands, execute immediately and update the same navigation/active-team state as mouse/keyboard menus.
- [ ] For `:team create` with no name, open the create-team dialog; with a complete valid name, create directly through the same use case and activate the new team.
- [ ] If command arguments are incomplete but meaningful, open the relevant dialog and prefill supplied values.
- [ ] If a name is ambiguous, open a selection dialog; never choose an arbitrary team.
- [ ] Register Help, About, and version-information navigation/actions so command users can reach top-bar content.
- [ ] Test each handler via the same application/use-case operation used by the menu/dialog path.

## Acceptance checks

- [ ] `:view ...` is a navigation shortcut and does not mutate domain data.
- [ ] Complete `:team switch` changes active team once and returns to the same body tab.
- [ ] Partial `:team create` opens a prefilled dialog; complete `:team create --name ...` validates and creates through the shared use case.
- [ ] Ambiguous/invalid targets leave state unchanged and provide a clear choice/error.
- [ ] Command and menu actions produce equivalent database state and audit behavior.
- [ ] No handler contains SQL or duplicates team validation rules.

## Dependencies / boundaries

- Depends on [2.24](2.24-team-flows-as-dialogs.md), [2.26](2.26-command-parser-registry.md), and completed team use cases.
- Money, development, parts, and event commands are added with their corresponding feature phases/Phase 8.
