# 2.5 — Add the team table migration

**Status:** Not started  
**Goal:** Add the first user-domain table without preloading any team or sample data.

## Proposed v1 fields

- Stable database ID.
- User-entered team name, trimmed and non-empty.
- Optional profile notes.
- Creation/update timestamps maintained as record metadata.
- Archive timestamp/state; archived rows remain available to history.

The proposed uniqueness rule is case-insensitive uniqueness across all teams, including archived teams, to avoid ambiguous switching and reuse. Confirm this rule before finalizing the migration.

## Work list

- [ ] Confirm the name uniqueness/case-normalization policy and record it in this file.
- [ ] Add one ordered schema migration for the team table and appropriate constraints/indexes.
- [ ] Do not add a default team row, demo data, assumed season, currency, balance, or roster.
- [ ] Keep SQL in the compiled migration list, not in the TUI or team repository.
- [ ] Add migration integration tests for the expected columns/constraints and empty table.
- [ ] Verify upgrading an existing version-1 database applies the migration once.

## Acceptance checks

- [ ] A newly migrated database contains the team table but zero team rows.
- [ ] Team IDs are stable and are not derived from names.
- [ ] Required/unique constraints match the recorded policy, including case-insensitive duplicate rejection if confirmed.
- [ ] Optional notes and archive state are represented without fabricating user-entered profile data.
- [ ] Re-running migrations does not recreate or duplicate the team schema.
- [ ] Migration tests use a temporary database and pass in the integration suite.
