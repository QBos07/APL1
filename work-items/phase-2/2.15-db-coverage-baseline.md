# 2.15 — Add a database code-coverage baseline

**Status:** Done (2026-11-24)
**Goal:** Use coverage after real repository/domain code exists to identify untested database paths, without inventing a quality percentage prematurely.

## Coverage configuration

Added [`scripts/coverage.sh`](../../scripts/coverage.sh). It:

- creates a fresh temporary build (or reuses `APL1_COVERAGE_BUILD_DIR`),
- configures with `--coverage -O0 -g` and CTest enabled,
- builds and runs only `apl1_unit_tests` (the SQLite-backed test executable),
- runs `gcov -b -c` over `CMakeFiles/apl_db.dir/src/db/*.gcno`, and
- writes per-source `.gcov` files and `summary.txt` under
  `<build>/coverage-db/`.

The normal build and CTest configuration are unchanged. The script has no
coverage threshold and never writes reports into the repository.

```sh
./scripts/coverage.sh
APL1_COVERAGE_BUILD_DIR=/tmp/apl1-cov ./scripts/coverage.sh   # keep the report
```

## Review of uncovered paths

The remaining uncovered lines are predominantly defensive/error branches:

- `connection.c`, `migrations.c`, and `path.c`: pre-existing allocation,
  foreign-key, malformed-migration, and filesystem error paths from Phase 1.
- `team_repository.c`: prepare/bind/finalize failures, list allocation failure,
  and the finalize error branch. Normal validation and not-found/conflict paths
  are covered.
- `settings_repository.c`: prepare/row-read failures and the "settings row
  missing" corruption branch.
- `transaction.c`: the commit-failure → rollback branch (including rollback
  failure) cannot be induced through the public API with a healthy temporary
  SQLite database; it would require a database-failure injection seam. The
  normal begin/commit/rollback/nested rejection/closed-connection paths are
  covered.

Focused tests added from this review:

- closed-connection checks for all team repository operations,
- blank-name CHECK-constraint rejection and missing-team archive,
- null/closed/zero-ID/invalid settings arguments,
- invalid transaction arguments, nested begin, and closed-connection begin.

No arbitrary global threshold is introduced. If transaction fault injection or
other database backends become necessary, add a focused test seam then rather
than building a speculative failure framework now.
