# 2.8 — Add team rename and archive operations

**Status:** Not started  
**Goal:** Let users maintain team identity and archive a workspace without destroying its records.

## Work list

- [ ] Add repository update/archive methods that preserve the team ID and update record metadata.
- [ ] Add use cases for rename and archive, reusing the validation/uniqueness policy from 2.7.
- [ ] Prevent archiving the last non-archived team.
- [ ] Keep archived team and related records retrievable for historical views but excluded from default active-team selection.
- [ ] Make archiving the currently active team work with the fallback rule from [2.9](2.9-active-team-setting.md); implement 2.9 first if needed.
- [ ] Add tests for rename, duplicate rename rejection, repeated archive behavior, last-team protection, and history retention.

## Acceptance checks

- [ ] Renaming changes the display name but not the stable team ID or links to prior records.
- [ ] Invalid/duplicate names leave the stored team unchanged.
- [ ] Archiving does not delete the team or its records.
- [ ] The last active team cannot be archived.
- [ ] If the archived team was active, a valid fallback is selected and the UI can explain the switch.
- [ ] Repeating an archive action is either an idempotent success or a clear state error, as documented.

## Dependencies / boundaries

- Depends on [2.6](2.6-team-repository-read-create.md), [2.7](2.7-team-create-validation.md), and [2.9](2.9-active-team-setting.md).
- Permanent deletion is out of scope.
