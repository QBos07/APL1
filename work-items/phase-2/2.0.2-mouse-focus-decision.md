# 2.0.2 — Decide the mouse and focus interaction model

**Status:** Not started  
**Goal:** Define mouse behavior alongside keyboard focus before reusable menus, tables, and forms are implemented.

## Work list

- [ ] Define how a click focuses a list row, form control, tab, or visible action.
- [ ] Define click/double-click/activation behavior consistently; avoid actions that write data on mere pointer movement or ambiguous clicks.
- [ ] Define scroll-wheel behavior for lists, tables, and forms, including which pane receives scrolling.
- [ ] Define how keyboard focus and mouse hover/selection are represented so the active target is always visible.
- [ ] Define a coordinate/hit-region strategy that is recalculated after resize and does not embed business actions in drawing code.
- [ ] Record the decisions before implementing Phase 2 screen widgets.

## Acceptance checks

- [ ] Every mouse action has an equivalent keyboard action for core workflows.
- [ ] Mouse clicks select/focus before activating when accidental activation would be costly.
- [ ] Scroll events are scoped to the relevant focused/hovered region by a documented rule.
- [ ] Hit regions are invalidated/recomputed when layout changes.
- [ ] Mouse support can be added without bypassing the shared app/use-case layer.

## Dependencies / boundaries

- Can be designed alongside [2.0.1](2.0.1-tui-layout-resize-decision.md).
- Do not implement every widget or add feature-specific mouse behavior in this decision task.
