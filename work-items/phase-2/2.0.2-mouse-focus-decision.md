# 2.0.2 — Decide the mouse and focus interaction model

**Status:** Done (2026-11-24)
**Goal:** Define mouse behavior alongside keyboard focus before reusable menus, tables, and forms are implemented.

## Decision

Focus is semantic screen state, not a plane, pointer, or drawing artifact. A
screen controller owns exactly one focused target (a row, field, tab, or action)
and, while a modal is open, the modal owns the only focusable targets. Mouse
input only moves focus and selects targets; activation goes through the same
command dispatch as the keyboard.

### Focus model

- Focus is a stable target identifier (`kind` plus a screen-local/row ID), not a
  `struct ncplane *`, a pointer into a list, or a rendered string.
- Each screen defines a deterministic focus order:
  1. modal controls when a modal is active (the background is a focus trap);
  2. otherwise navigation (section tabs/team switcher);
  3. the primary region (list/table rows, or form fields in visual order);
  4. the actions line.
  The status line is informational and never focusable.
- `Tab`/`Shift+Tab` move to the next/previous focus group and wrap within the
  screen. Arrow keys move within the focused collection. `Enter`/`Space` activate
  the focused target. `Esc` closes the modal/transient surface first, then goes
  back one screen; it never discards a modified form without confirmation.
- A focused target that is off-screen is scrolled into view before the frame is
  rendered, so focus is always visible.
- Disabled actions remain focusable so activation can explain why they are
  unavailable in the status line; they are never silently skipped or executed.
- Closing a modal restores the focus target that was active before it opened, if
  that target still exists; otherwise focus falls back to the first target of
  the parent screen.
- `q` quits only when focus is not a text-entry field and no modal is active;
  inside a text field it is typed normally.

Visual representation is textual as well as stylistic: focus uses a leading `>`
marker and highlight; the selected row uses a marker plus reverse video; the
active tab uses brackets/underline rather than color alone. Disabled targets are
marked unavailable and give a reason when focused.

### Mouse activation

Mouse reporting is enabled with `notcurses_mice_enable(nc, NCMICE_BUTTON_EVENT)`
only. Move and drag events are deliberately not requested in v1, so there is no
hover state: pointer movement never changes focus, selection, scrolling, or data.
If enabling mouse reporting fails, the application continues keyboard-only and
may note that mouse support is unavailable in the status line.

Only `NCTYPE_PRESS` on button 1 (left) and wheel buttons 4/5 are acted on.
Release and repeat events are ignored. A press is resolved through the current
hit-region map (below); the topmost modal region wins over background regions.

| Target | Left click | Double click | Keyboard equivalent |
| --- | --- | --- | --- |
| List/table row | Focus and select the row; no navigation or write | Activate the selected row (open detail/view) | Arrows select; `Enter` opens |
| Section tab / team/menu item | Focus and activate (switch context) | Same as single click | `Tab` to navigation, arrows, `Enter` |
| Action button | Focus and activate | Same as single click | `Tab` to action, `Enter`/`Space` |
| Destructive/archive action | Focus and open its confirmation dialog | Same as single click | `Enter` opens the same confirmation |
| Disabled action | Focus and show the reason | Same as single click | Focus shows the reason; no execution |
| Form field | Focus the field; does not edit or save | Same as single click | `Tab`/arrows focus; typing edits |
| Form Save / Cancel | Focus and activate; validation errors keep typed values | Same as single click | `Tab` to the button, `Enter`/`Space` |
| Empty region / outside modal | Focus the owning region if focusable; otherwise no-op. Never closes a modal | Same as single click | No direct action |

A double click means two left-button presses on the same target within
`APL_TUI_DOUBLE_CLICK_MS` (500 ms, measured with `CLOCK_MONOTONIC`). The first
press still selects/focuses; only the second activates a row. A second press on a
different target is a new single click. There is no OS double-click setting to
consult, so the threshold is fixed and documented.

Any mouse navigation that would leave a modified form (tab, menu, team switch,
row open) goes through the same unsaved-changes confirmation as the keyboard
action. Clicking a tab or action never silently discards typed values.

Mouse actions that are not in the table do nothing: right/middle buttons are
reserved, and there is no drag, hover, or drag-select in v1. A row click never
writes data; all writes require an explicit action control and the usual
confirmation/validation path. Clicking outside an open modal does not dismiss it,
so an accidental click cannot discard a dialog.

### Scroll model

Wheel events are scoped by pointer position first, then focus:

- If a modal is open, only the topmost scrollable region in the modal is scrolled;
  wheel events over the background are ignored.
- Otherwise, if the pointer is over a scrollable region, that region scrolls.
- Otherwise the currently focused scrollable region scrolls.
- If neither exists, the event is ignored.

In a list/table, one wheel event moves focus and selection by
`APL_TUI_SCROLL_STEP` rows (3) with clamping, so the focused row remains visible.
In a read-only detail pane, the wheel scrolls the viewport without changing the
focused target. Forms scroll the focused pane/page. Horizontal wheel events are
ignored in v1; basic table use must not require horizontal scrolling.

Keyboard equivalents are one row (`Up`/`Down`), one page (`PageUp`/`PageDown`),
and first/last (`Home`/`End`) in the focused region. Wheel scrolling never
activates a target, changes screens, or writes data.

### Hit regions

Hit regions are pure screen-layout data, not drawing callbacks:

```c
typedef enum apl_tui_hit_kind {
    APL_TUI_HIT_NONE,
    APL_TUI_HIT_ROW,
    APL_TUI_HIT_TAB,
    APL_TUI_HIT_BUTTON,
    APL_TUI_HIT_FIELD,
    APL_TUI_HIT_PANE,
} apl_tui_hit_kind;

typedef struct apl_tui_hit_region {
    apl_tui_rect rect;              /* absolute terminal cells */
    apl_tui_hit_kind kind;
    uint64_t target_id;             /* stable row/control ID, never a pointer */
    bool enabled;
} apl_tui_hit_region;
```

- A screen builds an ordered hit-region list from its layout and current content,
  not from draw calls. Drawing consumes the same layout data, so a visual control
  and its hit area cannot drift apart.
- Region rectangles are absolute terminal cells, matching `ncinput.y`/`ncinput.x`.
  Coordinates of `-1` and coordinates outside all regions resolve to
  `APL_TUI_HIT_NONE`.
- Modal regions are checked first, then background regions. Persistent frame
  regions do not overlap by construction; the overlay may cover part of the body.
- A list only registers hit regions for visible rows, using the current scroll
  offset. Scrolling or changing content rebuilds those regions.
- Stable IDs come from the persisted record ID when one exists (for example a
  team/row ID); transient rows use a screen-local monotonic counter. Pointers,
  row text, and plane addresses are never target IDs.
- The hit-region list is invalidated and rebuilt whenever the layout, screen,
  content, or scroll offset changes, and always after `NCKEY_RESIZE` before the
  next input event is dispatched. The list is never reused across a resize.
- Hit-testing returns `kind` and `target_id` only. The controller maps that target
  to the same command the keyboard would invoke; no drawing or hit-region code
  performs business logic, constructs SQL, or writes data.

### Keyboard coverage

Every core mouse workflow has a documented keyboard path:

- focus/select a row: arrow keys;
- open a row: `Enter`;
- switch sections/tabs/teams: navigation focus plus arrows and `Enter`;
- activate an action: `Tab` plus `Enter`/`Space`;
- dismiss a dialog: `Esc` or the focused Cancel/Close action;
- scroll: arrows, `PageUp`/`PageDown`, `Home`/`End`.

Mouse support therefore remains an optional accelerator, not a requirement for
any workflow. The named constants (`APL_TUI_DOUBLE_CLICK_MS`,
`APL_TUI_SCROLL_STEP`) land with the widget implementation in 2.3/2.4.

### What is unit-testable without a terminal

- Hit-testing against synthetic layout/hit-region lists, including overlay-first
  precedence and `-1`/out-of-range coordinates.
- Focus transitions for keyboard and synthesized mouse events, modal focus
  trapping/restoration, and selection/scroll arithmetic.
- Double-click matching (same target within the threshold) with an injected
  timestamp; no wall-clock dependency in tests.

Actual terminal mouse reporting and rendered focus styling are verified in the
interactive smoke/manual check when reusable widgets land in 2.3/2.4. Tests must
not require an interactive terminal.
