# 2.0.3 — Define repository, statement, and transaction ownership

**Status:** Done (2026-11-24)
**Goal:** Set a clear persistence boundary before the team schema/repository work begins.

## Decision

The proposed contract is confirmed with these concrete rules:

| Resource | Owner | Lifetime | Everyone else |
| --- | --- | --- | --- |
| `sqlite3 *` connection | `apl_app` (`app->db`) | Opened by `apl_app_start`, closed by `apl_app_stop` | Repositories/use cases borrow it for one call; never open or close it |
| `sqlite3_stmt *` | The repository function that prepares it | Created and finalized inside that call | Never escapes a repository through an output parameter or header |
| Transaction | A use case in `src/app` | Explicit begin/commit/rollback around a multi-write operation | Repositories never begin, commit, or roll back |
| Error context | Layer that detects the failure | One `apl_error` value owned by the caller | Higher layers add context with `apl_error_prefix`; no global error state |

The application remains single-threaded. SQLite handles are not shared between
threads, and no mutex, statement cache, or connection pool is introduced.
`src/domain` stays pure validation/business-rule code and never receives a
connection; `src/app` runs domain validation, then owns any transaction.

### Connection ownership

- `apl_app` owns the only production connection. It is opened after the TUI has
  verified a usable terminal and after path resolution/migration, and closed on
  every exit path through `apl_app_stop`.
- Repositories borrow `apl_db_connection *` or, inside the database layer, the
  handle from `apl_db_handle`. They never call `sqlite3_open*` or
  `sqlite3_close*`.
- A repository call with a null/closed connection returns
  `APL_ERR_INVALID_ARGUMENT` before preparing SQL; it does not dereference a
  null handle.
- TUI screens never hold a connection or include repository headers. They call
  application use cases, which borrow the app-owned connection.

### Statement ownership

- Every public repository call prepares at most one statement in v1. The
  statement is a local variable finalized before every return, including:
  prepare failure (nullptr is safe to finalize), bind failure, step failure, and
  success.
- A repository uses one cleanup path so a new early return cannot skip
  `sqlite3_finalize`. No `sqlite3_stmt *` appears in a production header, output
  parameter, callback, or long-lived struct.
- Bind borrowed text/blob values with `SQLITE_TRANSIENT` unless the call
  guarantees the value outlives the step. The default is copying, which avoids
  dangling binds from screen-owned strings.
- Check `sqlite3_prepare_v2`, every bind, `sqlite3_step`, and `sqlite3_finalize`.
  Capture `sqlite3_errmsg` before finalizing when reporting a failed step.
- For updates/deletes/gets that require an existing row, zero affected rows
  (`sqlite3_changes`) or a missing query row maps to `APL_ERR_NOT_FOUND` with the
  entity and ID in the message.
- `sqlite3_last_insert_rowid` is read only after a successful insert on the same
  connection; the single-threaded rule makes this safe.
- There is no prepared-statement cache in v1. If measurement later justifies one,
  it must be an internal database-layer detail with explicit lifetime rules; it
  does not change the public repository contract.

### Transaction ownership

A multi-write use case owns the boundary. Repositories remain single-operation
primitives; they never start, commit, or roll back a transaction and cannot
accidentally end a use-case-owned one.

The database layer exposes the helper in `src/db/transaction.{h,c}` (implemented
with the first real transaction user in Phase 2):

```c
typedef struct apl_db_transaction {
    apl_db_connection *connection; /* borrowed; never owned */
    bool active;
} apl_db_transaction;

apl_status apl_db_transaction_begin(apl_db_transaction *tx,
                                    apl_db_connection *connection,
                                    apl_error *error);
apl_status apl_db_transaction_commit(apl_db_transaction *tx, apl_error *error);
apl_status apl_db_transaction_rollback(apl_db_transaction *tx, apl_error *error);
```

Contract:

- `begin` requires an open connection, an inactive transaction value, and
  `sqlite3_get_autocommit(handle) != 0`. A nested begin is rejected as
  `APL_ERR_INVALID_ARGUMENT`; savepoints/nested transactions are not supported in
  v1. It issues `BEGIN IMMEDIATE` so the write lock is acquired before the first
  write and partial work is not started while waiting for a lock.
- `commit` requires an active transaction, issues `COMMIT`, and clears `active`
  on success. If `COMMIT` fails, the helper makes a best-effort `ROLLBACK` (if
  SQLite still reports an active transaction), clears `active`, reports the
  commit failure, and never claims the work succeeded. Any rollback failure is
  added as context without replacing the commit error.
- `rollback` is safe and idempotent on an inactive transaction (returns
  `APL_OK`), so cleanup paths may call it unconditionally. On an active
  transaction it issues `ROLLBACK` and clears `active` on success.
- The helper never owns or closes the connection. Calling it after the connection
  is closed is a caller bug reported as `APL_ERR_INVALID_ARGUMENT`; cleanup order
  is transaction, then connection.
- The existing migration runner's private transaction code is an internal
  database-layer implementation detail; new repository/use-case work uses this
  helper. It may be aligned with the helper later without changing the migration
  contract.

Failure and rollback behavior:

1. On an operation failure, the use case calls `apl_db_transaction_rollback`.
2. If rollback succeeds, the original status and message are returned unchanged.
3. If rollback also fails, keep the original status code and use
   `apl_error_prefix` with a bounded context such as
   `"rollback failed: <rollback message>"`. The final message retains the original
   operation detail rather than being replaced by the rollback error.
4. The use case never returns without either committing or rolling back. A
   failed commit already performs the best-effort rollback described above.

### Error context

- `src/db` translates SQLite failures into `APL_ERR_DB_QUERY` with a concrete
  operation and the SQLite message, for example
  `"insert team failed: UNIQUE constraint failed: teams.name"`.
- Missing expected rows use `APL_ERR_NOT_FOUND`; invalid arguments use
  `APL_ERR_INVALID_ARGUMENT`; no new business status is required by this decision.
- Application/use-case code adds action context with `apl_error_prefix`, for
  example `"create team"` in front of the repository message. The TUI displays
  `apl_error_message` and does not parse SQLite text.
- Expected business-rule failures (blank name, duplicate policy) are validated by
  use cases before the repository call. If a constraint still fires, it is
  reported as a database failure; the repository does not invent user-facing
  duplicate policy and no new status code is appended in this decision.
- SQL text, statement pointers, and connection pointers never appear in public
  messages.

### Include and link visibility

- Repository implementations live in `src/db/` and compile into the existing
  `apl_db` target. Public production headers are included as
  `"db/<module>.h"`; repository headers expose only `apl_db_connection` and
  domain/use-case structs, not `sqlite3_stmt`.
- `apl_db` keeps `apl_core` and SQLite as `PUBLIC` dependencies because
  `connection.h` exposes the borrowed `sqlite3 *` type. SQL text stays in `.c`
  files.
- `apl_app` links `apl_db` publicly to implement use cases. `apl_tui` calls
  `apl_app` use cases and does not include `db/` repository headers or link SQL
  itself.
- `tests/support` headers remain private to test executables through
  `apl_test_support`; no production target exposes or links a `tests/` include
  path. Repository integration tests use the production repository API and a
  temporary database, never a test-only statement handle.
- No generic repository framework, ORM, query builder, or unit-of-work layer is
  introduced. Add concrete per-entity functions as features need them.

### Example: create team and activate it atomically

```c
apl_status apl_team_create_and_activate(apl_app *app, const char *name, ...,
                                        apl_error *error)
{
    apl_db_transaction tx = {};
    apl_status status = apl_db_transaction_begin(&tx, &app->db, error);
    if (status != APL_OK) {
        return status;
    }

    int64_t team_id = 0;
    status = apl_team_repository_insert(&app->db, name, ..., &team_id, error);
    if (status == APL_OK) {
        status = apl_settings_repository_set_active_team(&app->db, team_id, error);
    }
    if (status != APL_OK) {
        const apl_status original = status;
        apl_error rollback_error;
        apl_error_init(&rollback_error);
        if (apl_db_transaction_rollback(&tx, &rollback_error) != APL_OK) {
            char context[160];
            snprintf(context, sizeof(context), "rollback failed: %s",
                     apl_error_message(&rollback_error));
            apl_error_prefix(error, original, context);
        }
        return original;
    }
    return apl_db_transaction_commit(&tx, error);
}
```

If the settings write fails (or the team insert violates a constraint), the
rollback removes the just-inserted team row and no active-team setting is left
behind. If the final commit fails, the helper attempts rollback and the caller
receives the commit failure; no partial success is reported.

This is illustrative: concrete repository/use-case signatures are defined by
2.6/2.9 when those operations land.

### Testing the contract

- Integration tests use a fresh temporary SQLite database and the production
  repository API.
- Commit persists both writes; an induced failure in the second write rolls back
  the first; the database contains neither partial record nor setting.
- A nested `begin` is rejected and leaves the outer transaction usable.
- A failed insert finalizes its statement (no leak) and reports the SQLite
  message with the operation context; a follow-up query on the same connection
  still works.
- Not-found and invalid-connection paths are covered without mutating the
  database.
- Tests must not require a terminal and must not include `sqlite3_stmt` from a
  production header.
