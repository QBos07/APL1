# 2.26 — Add the command parser and registry

**Status:** Not started  
**Goal:** Parse concise colon commands into typed requests and provide useful help/completion without shell or SQL execution.

## Work list

- [ ] Define a small command registry with command name, aliases, usage, required options, and handler ID.
- [ ] Parse a leading colon, command words, quoted strings, and `--name value` options; report token/option errors clearly.
- [ ] Distinguish unknown command, incomplete command, complete command, and invalid value outcomes.
- [ ] Provide command-specific help and completion suggestions from the registry.
- [ ] Preserve arguments as data; never pass command text to a shell or SQLite interpreter.
- [ ] Add unit tests for whitespace, quoting, missing values, unknown options, incomplete commands, aliases, and help/completion.
- [ ] Ensure the parser itself has no Notcurses or SQLite dependency.

## Acceptance checks

- [ ] Same input deterministically produces the same typed command request or parse error.
- [ ] Quoted team names with spaces and punctuation are parsed as one value.
- [ ] Incomplete vs invalid commands are distinguishable so the UI can open a form for the former.
- [ ] `:help` and command-specific help are generated from registered usage, not duplicated strings.
- [ ] Arbitrary shell/SQL-looking input is treated as invalid command text and never executed.
- [ ] Tests cover parser boundaries without a terminal or database.

## Dependencies / boundaries

- Depends on [2.25](2.25-ex-command-line-ui.md).
- Command handlers and menu parity are [2.27](2.27-core-command-actions.md); feature-specific commands are added in Phase 8.
