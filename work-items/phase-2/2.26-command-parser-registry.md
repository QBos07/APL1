# 2.26 — Add the command parser and registry

**Status:** Complete (2026-11-24)  
**Goal:** Parse concise colon commands into typed requests and provide useful help/completion without shell or SQL execution.

## Work list

- [x] Define a small command registry with command name, aliases, usage, required options, and handler ID.
- [x] Parse a leading colon, command words, quoted strings, and `--name value` options; report token/option errors clearly.
- [x] Distinguish unknown command, incomplete command, complete command, and invalid value outcomes.
- [x] Provide command-specific help and completion suggestions from the registry.
- [x] Preserve arguments as data; never pass command text to a shell or SQLite interpreter.
- [x] Add unit tests for whitespace, quoting, missing values, unknown options, incomplete commands, aliases, and help/completion.
- [x] Ensure the parser itself has no Notcurses or SQLite dependency.

## Acceptance checks

- [x] Same input deterministically produces the same typed command request or parse error.
- [x] Quoted team names with spaces and punctuation are parsed as one value.
- [x] Incomplete vs invalid commands are distinguishable so the UI can open a form for the former.
- [x] `:help` and command-specific help are generated from registered usage, not duplicated strings.
- [x] Arbitrary shell/SQL-looking input is treated as invalid command text and never executed.
- [x] Tests cover parser boundaries without a terminal or database.

## Dependencies / boundaries

- Depends on [2.25](2.25-ex-command-line-ui.md).
- Command handlers and menu parity are [2.27](2.27-core-command-actions.md); feature-specific commands are added in Phase 8.

  typed handler ids. Parsing handles leading `:`, whitespace, single/double
  quotes with escapes, `--name value`, and `--name=value`.
- Unknown, incomplete, and invalid outcomes are distinct; help/completion are
