# 2.22 — Add a consistent color theme

**Status:** Not started  
**Goal:** Make the interface feel like a polished modern TUI while retaining readable operation on limited-color terminals.

## Work list

- [ ] Define semantic style roles for window bar, dropdown, active tab, inactive tab, active team, body, selection/focus, dialog, success, warning, and error.
- [ ] Implement styles centrally so screens do not invent incompatible color pairs.
- [ ] Check terminal color capability and fall back to text markers/bold/reverse styles when colors are unavailable.
- [ ] Use readable contrast and avoid using hue as the sole signal for status or focus.
- [ ] Keep colors stable across resize/redraw and when dialogs/menus are open.
- [ ] Add a style-role test and manual checks in full-color and restricted/no-color terminals.
- [ ] Expose theme selection only if a real alternate theme is implemented; otherwise keep Settings entry as a clear future placeholder.

## Acceptance checks

- [ ] The top bar, tab rail, body, status bar, menus, and dialogs share one coherent palette.
- [ ] Active tab/team, keyboard focus, selected row, success, warning, and error are visually distinct.
- [ ] Text/markers preserve the distinction in monochrome or limited-color modes.
- [ ] No individual screen hard-codes an unrelated palette.
- [ ] Color initialization failure does not prevent keyboard/mouse use.

## Dependencies / boundaries

- Depends on [2.16](2.16-redesign-layout-geometry.md); can be developed alongside 2.18–2.21.
- User-configurable theme editing is out of scope unless implementation experience makes it a small, clear addition.
