# 2.9 — Add a persisted active-team setting

**Status:** Not started  
**Goal:** Persist the selected team by stable ID and recover safely if that team is no longer active.

## Work list

- [ ] Add a small settings/app-state migration for the active team ID; do not store a team name as identity.
- [ ] Add repository operations to read and set the selected team ID.
- [ ] Add an application/use-case operation that selects only a non-archived team.
- [ ] Persist the setting across connection close/reopen and application restart.
- [ ] Define and implement the deterministic fallback: choose the oldest-created non-archived team (stable ID as tie-breaker) if the stored ID is missing/archived; return a notice explaining the fallback.
- [ ] Define the no-active-team behavior for an empty database and handle stale/dangling IDs safely.
- [ ] Add integration tests for selection persistence, invalid selection, archived selection, fallback, and empty state.

## Acceptance checks

- [ ] Active team is stored and retrieved by stable ID, not by mutable name.
- [ ] Selecting a nonexistent or archived team is rejected without changing the stored selection.
- [ ] On startup, a stale/archived selection resolves to the documented fallback and reports that it changed.
- [ ] An empty team table produces a no-active-team state, not an error or fabricated row.
- [ ] Fallback and setting updates are transactionally consistent with archiving where applicable.

- Depends on [2.5](2.5-team-schema.md), [2.6](2.6-team-repository-read-create.md), and the Phase 1 migration/app lifecycle.
- The team picker UI is [2.10](2.10-team-switcher-screen.md).
