# 2.14 — Add a team-isolation integration test

**Status:** Not started  
**Goal:** Prove persisted team operations and active-team selection do not leak data across workspaces.

## Work list

- [ ] Create two teams through the public application/use-case path in a temporary SQLite database.
- [ ] Add distinguishable notes/profile values and select each team in turn.
- [ ] Verify list/get/update operations return or modify only the requested team.
- [ ] Verify active-team selection persists by ID after closing/reopening the app/database.
- [ ] Verify archiving one team preserves its detail but excludes it from the default active list and chooses the documented fallback.
- [ ] Verify the last remaining team cannot be archived.
- [ ] Keep fixtures fully user-created by the test; do not rely on seed rows.

## Acceptance checks

- [ ] Team A's data is not returned when querying team B and vice versa.
- [ ] Renaming one team does not change the other team's ID, data, or active selection.
- [ ] Active-team restoration and archive fallback match the documented behavior.
- [ ] All writes are made through public use cases/repositories, not test-only direct SQL except setup assertions where necessary.
- [ ] The test uses an isolated temporary database and passes in the regular SQLite integration suite.
