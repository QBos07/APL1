# 1.7 — Prove migration failures roll back

**Status:** Not started  
**Goal:** Demonstrate that a failed schema migration does not leave a partially applied schema or a falsely recorded version.

## Work list

- [ ] Ensure the migration runner wraps a migration's statements and version insertion in one transaction.
- [ ] Add a test-only migration that makes one valid schema change and then deliberately fails.
- [ ] Run that migration against a temporary database and capture the returned error.
- [ ] Inspect the database after failure for partial schema changes and version records.
- [ ] Re-run a valid migration path against the same database if the runner contract allows recovery; otherwise document that a fresh database is required after a failed migration.
- [ ] Keep the deliberate failure out of production migration registration.

## Acceptance checks

- [ ] The deliberately failing migration returns a useful failure.
- [ ] Its transaction leaves no partial table/index/data change.
- [ ] Its version is not recorded as applied.
- [ ] A subsequent valid migration run behaves according to the documented recovery contract.
- [ ] The test does not modify a developer's real database.

## Dependencies / boundaries

- Depends on [1.5](1.5-migration-runner.md) and [1.6](1.6-initial-migration.md).
- Do not add production recovery, backup, or migration downgrade systems in this task.
