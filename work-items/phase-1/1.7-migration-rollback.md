# 1.7 — Prove migration failures roll back

**Status:** Done  
**Goal:** Demonstrate that a failed schema migration does not leave a partially applied schema or a falsely recorded version.

## Implementation notes (2026-11-24)

- The runner (1.5) already wraps each migration's statements and its version INSERT
  in one `BEGIN IMMEDIATE` ... `COMMIT` transaction; this item proves the behavior.
- Recovery contract (documented in `src/db/migrations.h` and here): a failed
  migration is not recorded as applied and leaves no partial schema change; a
  corrected version of the same migration can be re-run against the same database
  on the next run. No production recovery/downgrade system is added.
- Tests: `tests/integration/test_db_migration_rollback.c`, using a test-only migration
  list (never registered in production `migrations_list.c`) where migration 2 first
  performs one valid schema change (`CREATE TABLE apl_roll_second`) and then fails
  (`INSERT INTO apl_roll_missing` — no such table):
  - the runner returns `APL_ERR_DB_MIGRATION` and the message contains the SQLite
    detail (`apl_roll_missing`);
  - after the failure: migration 1 remains applied with exactly one version record
    (version 1), migration 2's table is absent, and no version-2 record exists;
  - a corrected version 2 run on the same database succeeds and reaches version 2.
- Tests use temporary directories only; they never touch a developer's real database.
