# 1.5 — Add schema versioning and a migration runner

**Status:** Not started  
**Goal:** Track the database schema version and apply ordered, versioned changes safely on startup.

## Work list

- [ ] Choose the v1 migration representation: migrations compiled into the application, not files that must be found in the current working directory.
- [ ] Create a schema-version table containing at least migration version and applied timestamp.
- [ ] Implement a runner that reads the current version and applies each missing migration in order.
- [ ] Apply each migration and its version record atomically in a transaction.
- [ ] Treat an unknown/newer database schema version as a clear compatibility error; do not downgrade or overwrite it.
- [ ] Define behavior for duplicate versions and gaps in the compiled migration list and test those failures.
- [ ] Add temporary-database tests for first initialization and repeated initialization.

## Acceptance checks

- [ ] A new database creates the version table and reaches the latest compiled version.
- [ ] Running migrations twice leaves the schema version and schema unchanged on the second run.
- [ ] Each successful migration has exactly one version record.
- [ ] A database newer than the application is not modified and produces an actionable error.
- [ ] Migration code is independent of TUI rendering and works with the database wrapper.

## Dependencies / boundaries

- Depends on [1.2](1.2-database-connection.md) and [1.4](1.4-foreign-keys.md).
- The initial empty schema baseline is [1.6](1.6-initial-migration.md); failure rollback behavior is [1.7](1.7-migration-rollback.md).
