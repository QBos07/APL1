# 1.5 — Add schema versioning and a migration runner

**Status:** Done  
**Goal:** Track the database schema version and apply ordered, versioned changes safely on startup.

## Implementation notes (2026-11-24)

- Module: `src/db/migrations.h` / `src/db/migrations.c` (library `apl_db`).
- v1 representation decision: migrations are compiled into the application as an
  ordered `{version, SQL}` array; nothing is loaded from the working directory.
- Version table: `apl_schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL)`
  with one row per applied migration; current version is `MAX(version)` or 0 when the
  table is absent (fresh database).
- `apl_db_migrations_run_list` validates the whole list before touching the database:
  versions must be exactly 1..count, contiguous and ascending (duplicates and gaps are
  `APL_ERR_DB_MIGRATION`). The version table is created if missing; a database whose
  version is newer than the compiled list is never modified and yields
  `APL_ERR_DB_SCHEMA_TOO_NEW` with actionable guidance.
- Each missing migration runs inside one `BEGIN IMMEDIATE` transaction with its
  version-record INSERT; failure rolls back and leaves no partial schema change and no
  version record (proven further in 1.7).
- The production compiled list entry point lands with the first migration (1.6);
  `apl_db_current_version` is available to callers (and 1.10).
- Tests: `tests/integration/test_db_migrations.c` — first run reaches the latest
  version with one record (with non-null timestamp) per migration, repeated run is a
  no-op (version, row count, and sqlite_master table count unchanged), newer database
  is refused without modification, duplicate versions and gaps are rejected before any
  database change, and a fresh database reports version 0.
