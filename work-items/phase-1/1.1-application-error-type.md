# 1.1 — Add an application error type

**Status:** Not started  
**Goal:** Give application and business-operation code a small way to report failures without depending on Notcurses or exposing SQLite-specific errors to every caller.

## Work list

- [ ] Add a small header/source module in the agreed application/shared location.
- [ ] Define a success/failure status and a concise error value suitable for C callers.
- [ ] Include a stable error category/code and a human-readable message; avoid hidden global “last error” state.
- [ ] Define who owns message memory and how callers initialize/clear an error value.
- [ ] Add focused tests for success initialization, failure creation, and message/code access.
- [ ] Keep SQLite and Notcurses error translation in their respective boundary modules.

## Acceptance checks

- [ ] The error type can be included by domain/application code without including SQLite or Notcurses headers.
- [ ] A caller can distinguish success from failure and retrieve a useful failure message.
- [ ] Ownership/lifetime is documented and no allocation is leaked in the tested lifecycle.
- [ ] Tests cover the type's public behavior; no terminal or database is needed.
- [ ] Strict project compiler warnings remain clean.

## Dependencies / boundaries

- Depends on [0.3](../phase-0/0.3-source-layout.md) and [0.4](../phase-0/0.4-code-conventions.md).
- Do not create a large error framework, exception emulation, or user-facing error dialog here.
