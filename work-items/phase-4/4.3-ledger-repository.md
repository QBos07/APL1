# 4.3 — Add ledger repository operations

**Status:** Done  
**Goal:** Provide small, parameterized persistence operations for immutable posted entries.

## Work list

- [x] Add transaction create, get-by-ID, and list operations to `src/db` using the repository ownership contract.
- [x] List by active team with stable date/creation ordering and optional date range, entry kind, and normalized category filters.
- [x] Return all fields needed by details, audit, totals, and correction workflows, including currency and correction relationship.
- [x] Ensure reads and writes require explicit team scope; reject or return not-found for an ID belonging to another team.
- [x] Keep statement binding, row conversion, allocation/error handling, and array-growth overflow checks consistent with existing repositories.
- [x] Add SQLite integration tests for create/get/list, filters, ordering ties, malformed rows where practical, and team isolation.

## Acceptance checks

- [x] All SQL values are bound parameters; user values are never interpolated into SQL.
- [x] List results are deterministic and filters compose without leaking another team's entries.
- [x] Repository failures return the established application error type and release statements/allocations.
- [x] No repository operation edits or deletes a posted entry.
- [x] Tests cover signed values, date/category filters, empty results, and cross-team isolation.

## Dependencies / boundaries

- Depends on [4.2](4.2-ledger-schema.md), [4.1](4.1-money-and-currency-policy.md), and ARCH-02 database growth/overflow helpers.
- Repository operations do not enforce all business validation and do not own the caller's transaction; use cases own atomic boundaries.
- Aggregate balance/report queries are specified in 4.7, not implemented as a mutable balance cache here.
