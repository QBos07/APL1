# 4.4 — Add amount and required-field validation

**Status:** Done  
**Goal:** Validate money-entry inputs in testable domain/application code before persistence or UI-specific handling.

## Work list

- [x] Reuse `src/domain/money` exact parsing and currency validation; do not add floating-point conversions.
- [x] Validate required team, entry kind, amount, date, category, and description fields according to the 4.1 policy.
- [x] Enforce the 4.1 sign convention: income and expense inputs are positive magnitudes; opening balance may be positive, zero, or negative; reversal/adjustment values are constructed by correction use cases, not accepted as ordinary user-entered income/expense amounts.
- [x] Reject excess decimal precision, overflow, unsupported currency, mismatched team currency, malformed dates, blank required text, and overlong values without silent truncation.
- [x] Return structured field-specific validation errors using the existing field identifiers and preserve entered values for form correction.
- [x] Add pure unit tests for boundaries and repository-backed tests proving invalid requests write nothing.

## Acceptance checks

- [x] Tests cover zero, negative, smallest/largest parseable amounts, integer overflow, excess precision, blank fields, whitespace, date boundaries, and currency mismatch.
- [x] Invalid input is reported against the relevant field without requiring Notcurses or SQLite for pure rules.
- [x] Validation failure has no database or audit side effects.
- [x] Valid input has one canonical amount/currency/date representation shared by command and form paths.
