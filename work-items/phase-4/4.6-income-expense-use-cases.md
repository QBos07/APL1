# 4.6 — Add income and expense use cases

**Status:** Done  
**Goal:** Post ordinary income and expense entries through shared validated operations with atomic history.

## Work list

- [x] Add income and expense application operations using the common money validation and repository APIs.
- [x] Accept a positive user-entered magnitude and store income as a positive balance delta or expense as a negative balance delta, following 4.1.
- [x] Validate team reporting currency and reject mixed currency instead of converting.
- [x] Save each ledger entry and its activity event in one transaction using `apl_use_case_*`; do not emit activity for failed or no-op writes.
- [x] Define the initial audit payload: action, entry kind, record identity, amount/currency, entered date, category, and description only as appropriate; do not copy unrelated or sensitive data.
- [x] Add service/repository integration tests for valid posts, invalid data, conflict/constraint mapping, rollback, audit contents, and team isolation.
- [x] Verify an expense is accepted even if it makes the derived balance negative or exceeds a future budget.

## Acceptance checks

- [x] Income/expense creation is callable without Notcurses and returns structured validation feedback.
- [x] Ledger and activity rows commit together or neither commits.
- [x] Posted values are not edited in place; correction is handled by 4.10.
- [x] An over-budget or negative-balance expense is not blocked by policy.
- [x] Tests prove active-team scope and no cross-team writes.

## Dependencies / boundaries

- Depends on 4.2–4.5, ARCH-01, ARCH-05, and the Phase 3 activity repository.
- Does not add UI, budget evaluation, or links to later Phase 5/6 records.
- Do not treat a budget plan as authorization or a spending limit.
