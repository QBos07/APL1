# 4.1 — Choose the v1 amount and currency policy

**Status:** Done  
**Goal:** Record the money rules that all Phase 4 storage, calculations, and UI must follow before adding ledger tables.

## Decision baseline

- Follow [ARCH-06](../architecture-hardening/ARCH-06-money-and-ledger-model.md): store amounts as signed `int64_t` minor units at scale 2; never use floating point for money.
- Each monetary amount has an ISO-style three-letter currency code. A team has one reporting currency in v1; reject a transaction in a different currency instead of converting it implicitly.
- The opening balance and all later posted entries use the same team reporting currency. A team with no configured currency cannot post money until the user chooses one.
- The stored signed amount is the change to the balance: income is positive, expense is negative, and an opening balance may be positive, zero, or negative. Income/expense forms accept a positive magnitude and the use case applies the sign; correction entries have the opposite/specified balance effect.
- Categories are user-entered labels, not a seeded list or a separate category-management feature in v1. Trim surrounding whitespace, require a nonblank value, and compare/group labels using the documented normalized form while preserving a readable display value.
- User-entered transaction dates are calendar dates, not UTC audit timestamps. Period boundaries and date ordering use the same documented date representation.
- Display values use exactly two fractional digits and a visible currency code; formatting must remain exact and handle signed boundary values.

## Decisions (implemented)

- Currency codes are normalized to exactly three ASCII letters in upper case
  (`eur` becomes `EUR`). Empty codes are unset, not a default currency.
- A team chooses its reporting currency explicitly. The currency can be changed
  only while the team has no ledger entries and no budget plans; otherwise the
  change is rejected because v1 does not convert posted amounts.
- Stored signed effects: opening balance keeps the entered sign (including
  zero), income is positive, expensed magnitudes are stored negative, a
  reversal is the exact opposite effect, and a replacement adjustment uses the
  original classification's sign. Each team has at most one opening balance;
  later changes use corrections.
- Category labels are trimmed and internal whitespace runs collapse to one
  space for display. The grouping key is that label lower-cased, so labels
  differing only by case or extra whitespace are equivalent.
- Transaction dates are user-entered calendar dates in `YYYY-MM-DD`. Date
  filters are inclusive at both ends, and lists order by entered date descending
  then stable ID descending.
- Display uses the currency code plus exactly two fractional digits. All
  arithmetic uses checked `int64_t` minor units and reports overflow.
- Budget plans store non-negative planned minor units for one explicit
  team/period/normalized-category scope. They never enter ledger or actual
  totals, and overspending is only a report warning.
