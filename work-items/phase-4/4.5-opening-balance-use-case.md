# 4.5 — Add the opening-balance use case

**Status:** Done  
**Goal:** Let a user establish a starting ledger position as an explicit, explainable entry.

## Work list

- [x] Add an opening-balance application operation that validates the active team, configured reporting currency, amount, entered date, category/label policy, and description.
- [x] Persist the opening balance as a ledger entry with the dedicated opening-balance kind; do not add or update a balance field.
- [x] Decide and enforce whether each team may have one opening-balance entry or multiple explicitly dated opening adjustments. Surface the rule in the UI and tests.
- [x] Append an activity event in the same caller-owned transaction, including only the concise fields approved by the money audit policy.
- [x] Add unit/service integration tests for positive, zero, and negative opening balances, missing currency, duplicate-policy behavior, rollback, and team scope.

## Acceptance checks

- [x] The displayed balance can be derived from this entry plus later ledger entries.
- [x] A rejected or failed save creates neither a ledger entry nor an activity event.
- [x] The opening entry is distinguishable in repository reads and activity history.
- [x] No UI or use case exposes a direct “set current balance” operation after the opening entry.

## Dependencies / boundaries

- Depends on 4.1–4.4, ARCH-01 transaction helpers, ARCH-05 money record-kind registration, and the activity repository from 3.5.
- This slice adds the application operation only; the guided form arrives in 4.9.
- Opening balances are user-entered facts, never inferred from team creation or seeded defaults.
