# 3.4 — Add user-created car/chassis records

**Status:** Not started  
**Goal:** Give each team a stable car/chassis reference that later development and part records can link to.

## Proposed record

- Stable ID and owning team ID.
- Required user-entered car label/identifier.
- Optional user-entered chassis identifier and notes.
- Archived state and system timestamps.

The app creates no default car and does not infer a car number, year, or chassis identity.

## Work list

- [ ] Confirm the minimal car/chassis fields and team-scoped uniqueness rule before schema work.
- [ ] Add a migration for car records, team foreign key, indexes, and uniqueness constraints.
- [ ] Add repository create/list/get/update/archive operations scoped by team.
- [ ] Add domain validation for required label and optional chassis/notes lengths.
- [ ] Keep chassis identifiers optional and preserve history through rename/archive.
- [ ] Add unit and SQLite integration tests for CRUD, uniqueness, archive, and isolation.
- [ ] Ensure no car/chassis rows are seeded by migration or team creation.

## Acceptance checks

- [ ] A team may have no car records; creating a team does not create a car.
- [ ] Car records are linked by stable ID and cannot be read in another team's default list.
- [ ] Duplicate identifiers follow the recorded uniqueness rule and are not silently merged.
- [ ] Optional chassis/notes fields can remain empty without placeholder data.
- [ ] Archived cars remain available for historical references but are not offered as current by default.

## Dependencies / boundaries

- Depends on Phase 2 team persistence and repository ownership rules.
- UI is [3.10](3.10-car-views.md).
- Parts inventory, fitment, performance data, and car configuration are out of scope.
