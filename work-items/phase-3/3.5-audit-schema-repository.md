# 3.5 — Add the audit/activity schema and repository

**Status:** Not started  
**Goal:** Store a durable, inspectable chronology of important local record actions without claiming security-grade compliance logging.

## Proposed schema

- An activity event: stable ID, optional team ID, occurrence timestamp, action, entity type, entity ID, and concise summary.
- A child field-change record: event ID, field key, old value, and new value as text (null/absent values represent create/archive transitions).
- Entity IDs are stable values but polymorphic; do not add a fake universal foreign key to every domain table.
- The application exposes append operations and read queries, not update/delete operations for prior audit entries.

## Work list

- [ ] Confirm event/change fields and append-only application behavior before migration.
- [ ] Add a migration for activity and field-change tables with indexes by team, time, and entity.
- [ ] Add a repository append operation that can save one event and its field changes atomically inside a caller-owned transaction.
- [ ] Add list/get queries with team scoping, date ordering, and entity filtering.
- [ ] Ensure timestamps use one documented UTC representation and are system metadata, not user-entered event dates.
- [ ] Avoid storing secrets or unrelated free-form personal data in audit payloads.
- [ ] Add integration tests for event/change persistence, ordering, filters, and rollback.

## Acceptance checks

- [ ] A database migration creates no audit rows; only user/app operations produce activity.
- [ ] An event and all field changes are committed together or none are.
- [ ] Audit entries can be queried by team/entity and ordered chronologically.
- [ ] Prior events cannot be modified/deleted through the application repository API.
- [ ] A failed write leaves neither a partial activity event nor orphaned change rows.
- [ ] Tests use temporary databases and the repository transaction contract.

## Dependencies / boundaries

- Depends on the Phase 2 repository/transaction ownership contract and test-support target.
- Team operation integration is [3.6](3.6-team-audit-events.md); field-level scope is [3.7](3.7-team-audit-change-policy.md).
- This is a local single-user history mechanism, not tamper-proof auditing or multi-user attribution.
