# 3.6 — Record team create, rename, and archive activity

**Status:** Implemented (2026-11-24)  
**Goal:** Make Phase 2 team mutations produce traceable audit events in the same transaction as the team change.

## Work list

- [x] Update team create use case to append a `team_created` activity event after obtaining the new stable team ID.
- [x] Update team rename use case to append a `team_renamed` event with a concise record reference.
- [x] Update team archive use case to append a `team_archived` event, including active-team fallback context where useful.
- [x] Use the same caller-owned transaction for team mutation, active-team fallback changes, and audit event insertion.
- [x] Keep audit repository calls out of TUI handlers; menus/dialogs/commands continue through the same team use cases.
- [x] Add integration tests for event contents and failure injection proving team and audit state roll back together.

## Acceptance checks

- [x] Each successful create/rename/archive action has exactly one corresponding activity event.
- [x] A rejected validation or failed database operation creates no audit event.
- [x] If audit insertion fails, the related team mutation and active-team change are rolled back.
- [x] Events reference the team by stable ID and remain available after team archive/rename.
- [x] Repeating an idempotent archive does not create misleading duplicate activity, according to the documented operation contract.

## Implementation notes (2026-11-24)

- `team_service` appends `team_created`, `team_renamed`, and `team_archived` events inside the same transaction as the team row, active-team setting, and fallback update. Switching the active team does not create an activity event.
- Create emits exactly one event; a no-op profile update emits none; repeated archive is idempotent and emits no duplicate event.
- Failure-injection tests create an `activity_events` trigger that aborts the insert and verify that team creation/archive and active-team changes roll back completely.
